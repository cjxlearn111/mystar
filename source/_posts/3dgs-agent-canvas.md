## 一、问题与成果

一句话定位：**解决 3DGS 资产生成后"难编辑、难交互、难传播"的断层问题。**

3D Gaussian Splatting（3DGS）在 2023 年之后的爆发，让高精度 3D 场景的生成门槛从"专业团队 + 数周"降到了"单张消费级显卡 + 分钟级"。但生成只是起点。当你拿到一个 `.ply` 或 `.splat` 文件，要让它变成别人能看、能转、能理解的展示内容，中间还隔着一条漫长的后处理链路。

我们的核心成果是：**一个以对话为入口的 Agent 编排工具，把"得到资产 → 可传播展示"的链路压到最短。**

用户打开一个网页，加载 3DGS 资产，然后像聊天一样告诉 Agent"帮我做一个 30 秒的导览，从正面推进到细节特写，配一段轻快的背景音乐"——Agent 自动完成机位捕捉、轨迹连线、解说文案、音乐匹配，最终一键导出可分享的视频或链接。

技术栈：3DGS 渲染（WebGL / Three.js）+ LLM Agent（自然语言意图解析 + 任务编排）+ 可视化无限画布（机位管理与轨迹编辑）+ 浏览器原生录制（MediaRecorder API）。

## 二、思考与推演路径

### S（情境）：生成端已经"民主化"，传播端还在"封建时代"

3DGS 的核心突破在于用 2D 图像反向重建 3D 辐射场，不再需要复杂的摄影测量流程。这意味着：

- 一个设计师用手机绕物体拍一圈，就能得到可用的 3D 资产；
- 一个房产中介用无人机飞一趟，就能生成可漫游的室内场景；
- 一个游戏爱好者用开源工具，就能把自己的手办数字化。

**生成端的门槛已经崩塌，但传播端的门槛依然高耸。**

### C（冲突）：后处理链路卡死了资产的流动

传统链路是这样的：

```
得到 3D 资产
  → 导入 Blender / Maya 清洗拓扑
  → 导出为引擎可用格式（FBX / glTF）
  → 在 Unity / Unreal 里搭建展示场景
  → 找背景音乐、撰写背景资料
  → 编写前端代码（或录屏）
  → 最终展示（网页 / 视频 / PPT）
```

这条链路里，每一步都需要不同的专业技能。3DGS 虽然跳过了"建模"环节，但剩下的"编辑 → 编排 → 包装 → 发布"依然是一个多工种协作的重量级流程。

**用户的真实痛点不是"不会做 3D"，而是"做好了 3D，却发不出去"。**

### 对比案例：SuperSplat 解决了"编辑"，但没解决"传播"

SuperSplat 是一个优秀的在线 3DGS 编辑器，支持裁剪、调色、导出压缩格式。它的价值在于把"专业软件里的操作"搬到了浏览器里。

但它的受众依然是"专业开发者"——你需要理解 3D 坐标系、相机参数、文件格式，才能用得起来。对于大众创作者（房产中介、电商运营、内容博主），SuperSplat 的门槛依然太高。

**我们需要的是"传播工具"，不是"编辑工具"。**

### Q（疑问）：如何让复杂的资产处理路径彻底隐形？

如果把链路抽象成"输入 → 处理 → 输出"，那么：

- **输入**：一个可用的 3DGS 资产（.ply / .splat / .ksplat）
- **处理**：机位设定 → 轨迹编排 → 文案撰写 → 音乐匹配 → 视觉包装
- **输出**：一个可分享的链接、一段视频、或一段嵌入代码

问题的核心是：**"处理"环节太重、太专业、太分散。**

### A（答案）：用 Agent 吞噬中间流程

我们的解法是把"处理"环节全部交给 Agent，用户只负责两件事：

1. **说清想要什么**（自然语言描述展示意图）
2. **确认或微调结果**（在可视化画布上点点拖拖）

链路被压成三段：

```
得到可用 3D 资产 → 进入 Agent 流程（对话生成设定） → 一键生成展示 / 链接
```

Agent 负责理解用户的展示意图，自动完成机位捕捉、轨迹连线、解说文案、音乐匹配等操作。用户不需要知道"机位"和"轨迹"的技术定义，只需要说"从正面推进到细节特写"，Agent 就会翻译成对应的 3D 操作。

## 三、核心链路与可视化设计

### 3.1 对话框：Agent 介入的唯一入口

整个系统的交互围绕一个对话面板展开。用户用自然语言描述展示需求，Agent 解析意图后生成可执行的操作序列。

**关键设计原则：**

- **不说废话**：Agent 的回复只包含"做了什么"和"接下来可以做什么"，不展开技术细节；
- **可撤销**：每一步操作都进入撤销栈，用户可以随时回退；
- **需要确认时给选项**：对于删除、批量修改等不可逆操作，Agent 先列出预览，等用户点击"执行"才生效；
- **指代消解**：支持"它""这个""上一个"等代词，Agent 根据上下文推断目标。

**示例对话流：**

```
用户：帮我做一个 30 秒的导览
Agent：当前只有 1 个机位，至少需要 2 个才能做导览。要我自动拍几个角度吗？
用户：好
Agent：自动拍了 4 个角度（环绕展示），已连成一条轨迹。现在可以播放导览，也可以继续调整。
用户：给第 2 个机位加一段解说
Agent：已写好解说："镜头推进到细节区域，材质纹理与光影关系一目了然。"
用户：背景音乐换轻快一点的
Agent：已匹配一段轻快的背景音乐（时长 32 秒，可随导览循环）。
用户：导出视频
Agent：成片好了：30.5 秒 · 1920×1080 · 4.2 MB，已弹出预览，可以直接下载。
```

### 3.2 无限画布：非线性编排的载体

为什么用无限画布，而不是传统的线性时间轴？

**原因一：3D 展示的本质是非线性的。**

一个 3D 资产有无数个可观看的角度，用户可能想从正面切入，也可能想从顶部俯瞰，还可能想先展示整体再推进细节。线性时间轴强迫用户按"从左到右"的顺序思考，而无限画布允许用户像摆放便签一样自由组织机位。

**原因二：机位之间的关系比顺序更重要。**

在无限画布上，机位是卡片，卡片之间的连线代表相机运动轨迹。用户可以直观地看到"从 A 到 B 是一条直线推进"，"从 B 到 C 是一个环绕"。这种空间化的表达比时间轴上的"第 3 秒到第 5 秒"更符合人类对 3D 运动的理解。

**原因三：支持发散式探索。**

用户可以先拍一堆机位（发散），再决定哪些保留、哪些删除、以什么顺序连接（收敛）。无限画布天然支持这种"先铺开后整理"的工作流，而线性时间轴在"铺开"阶段就会显得拥挤。

### 3.3 视角选定与预设功能：降低 3D 交互门槛

3D 视角控制是大多数用户的痛点。我们做了两层简化：

**第一层：预设运镜。**

Agent 内置了几种常见的相机运动模式：

- **环绕展示**：相机围绕模型中心做 360 度水平环绕；
- **推进特写**：从当前位置直线推进到模型表面某一点；
- **俯瞰全景**：从顶部斜向下俯瞰整个场景；
- **升降扫视**：从低角度缓缓抬升到高角度。

用户不需要手动调整相机位置，只需要说"环绕一圈"或"推进到那个角"，Agent 自动计算相机路径。

**第二层：点击即中。**

在 3D 视口里，用户可以直接点击模型表面，Agent 把点击点解析为世界坐标，然后决定"相机应该放在哪里、看向哪里"。这比自己用鼠标拖拽旋转、滚轮缩放要直观得多。

## 四、开发踩坑实录

### 4.1 难点一：Agent 生成的参数如何与 3D 画布精准对齐

**问题：** Agent 用自然语言描述相机运动，比如"从正面推进到细节特写"，但 3D 画布需要具体的相机位置（pos）、目标点（target）、视场角（fov）三个向量。

**解法：** 不直接让 Agent 生成数值参数，而是让 Agent 生成"相对意图"，再由页面侧的适配层翻译成具体参数。

具体链路：

1. Agent 输出命令：`{ type: 'capture_keyframe', shot: 'close_up', target: 'surface_point' }`
2. 页面侧读取当前 3D 场景的几何信息（包围盒、表面采样点）
3. 根据预设运镜模板（close_up 对应"距离表面 1.5 倍包围盒半径、视线垂直于法线"）计算具体 pos / target
4. 执行捕捉，生成机位卡片

**关键洞察：** Agent 不应该知道"相机在哪里"，它只需要知道"用户想看什么"。具体的数值计算交给了解场景几何的页面侧。

### 4.2 难点二：3D 资产在网页端加载的性能与卡顿

**问题：** 一个 3DGS 资产可能包含数百万个高斯点，直接在网页端加载会导致：

- 首次加载时间长（几十 MB 的文件下载）；
- 渲染帧率低（移动端尤其明显）；
- 内存占用高（浏览器标签页容易崩溃）。

**解法：** 三层渐进加载 + 运行时动态降级。

**第一层：格式压缩。**

使用 `.ksplat` 格式（相比原始 `.ply`，体积缩小 60% 以上），并在服务端根据设备能力返回不同精度版本（桌面端给完整版，移动端给降采样版）。

**第二层：渐进渲染。**

先加载一个低分辨率的预览版本（类似图片的"模糊到清晰"渐进加载），让用户立刻看到模型轮廓；然后在后台线程里逐步加载高精度数据，替换掉低精度版本。

**第三层：运行时降级。**

监测渲染帧率，如果连续 3 秒低于 30fps，自动触发降级：

- 减少每帧渲染的高斯点数量（按距离裁剪远处的点）；
- 降低渲染分辨率（用 0.75x 或 0.5x 的物理分辨率）；
- 关闭抗锯齿和后期效果。

当帧率恢复后，再逐步升回高质量设置。

### 4.3 难点三：Agent 的"幻觉"与不可撤销操作

**问题：** LLM 偶尔会生成不合理的操作序列，比如"删除所有机位"或"把机位连成一个环导致播放死循环"。如果直接执行，用户可能丢失工作成果。

**解法：** 校验层 + 快照回滚 + 确认机制。

**校验层：** 在执行任何命令前，先跑一遍合法性检查：

- 删除操作：目标机位是否存在？
- 连线操作：是否会成环？起点和终点是否是同一个机位？
- 播放操作：机位数量是否 ≥2？是否连成了一条完整的链？

**快照回滚：** 每次执行操作前，先对当前场景打快照（包括机位卡片、连线、位置、元数据）。如果执行过程中任何一步报错，立刻用快照还原，保证用户数据不会处于"半完成"的脏状态。

**确认机制：** 对于删除、批量修改、多步组合操作，Agent 先列出预览（"我准备删除 3 个机位：A、B、C"），等用户点击"执行"才生效。用户随时可以说"取消"。

## 五、产品复盘与未来迭代

### 5.1 当前局限

**局限一：Agent 的生成准度依赖大模型能力。**

目前的意图解析基于规则 + 预设模板，对于复杂的多步指令（"先拍一个正面，然后环绕半圈，再推进到左上角那个凹陷处"）理解不够稳定。完全依赖 LLM 的话，延迟和成本都会上升。

**局限二：3D 交互的"精准性"与"简洁性"存在张力。**

点击即中的交互很直观，但有时候用户想精确控制相机高度或距离，这时候自然语言反而不如直接拖拽。我们在"对话优先"和"手动微调"之间做了折中：Agent 负责"大致到位"，用户可以在画布上拖拽机位卡片做像素级调整。

**局限三：音乐匹配和文案生成还比较粗糙。**

目前音乐匹配基于"情绪标签"（轻快 / 庄重 / 悬疑）做简单映射，文案生成基于模板填充。距离"根据模型内容自动生成个性化解说"还有一段距离。

### 5.2 下一步计划

**方向一：从"单资产展示"扩展到"多资产对比"。**

无限画布天然支持多资产并排摆放。下一步可以让用户同时加载多个 3DGS 模型（比如同一产品的三个配色版本），Agent 自动生成对比导览（"先看 A 的正面，然后切换到 B 的同一角度，注意看材质差异"）。

**方向二：从"导览视频"扩展到"交互式嵌入"。**

目前输出主要是视频和链接。下一步可以生成一段可嵌入网页的交互式代码（类似 YouTube 嵌入代码），让观看者在自己的浏览器里自由旋转、缩放、切换机位。

**方向三：从"通用 Agent"扩展到"垂直场景模板"。**

不同行业对 3D 展示的需求差异很大：

- 房产：重点在"空间尺度感"和"户型动线"；
- 电商：重点在"材质细节"和"多角度对比"；
- 文旅：重点在"氛围营造"和"历史背景解说"。

可以针对垂直场景预置 Agent 模板，用户选择"房产展示"后，Agent 自动采用对应的运镜策略、解说风格、音乐库。

**方向四：从"本地处理"扩展到"云端协作"。**

目前的处理全部在浏览器端完成，受限于设备性能。下一步可以把重计算（如高精度渲染、视频编码）放到云端，浏览器只负责预览和交互。同时支持多人协作：一个团队可以共同编辑同一个 3D 展示项目，Agent 记录每个人的修改历史。

## 六、结语

3DGS 技术让"生成 3D 资产"变得民主化，但"传播 3D 资产"依然是一个专业门槛极高的环节。我们的判断是：**下一代 3D 工具的核心竞争力不在"生成能力"，而在"传播效率"——也就是让 3D 内容以最低的成本、最短的路径到达最终受众。**

Agent 的价值不是替代专业人士，而是把"专业人士才能做的事"变成"会说话就能做的事"。当传播链路被压到最短，3D 资产才能真正从"技术 demo"变成"日常内容"。
